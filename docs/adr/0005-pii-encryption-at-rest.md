# ADR-0005: 家长 PII 静态加密（草案——评审后再实施）

- 状态：**草案（Proposed）**——待评审，未实施
- 日期：2026-09-10
- 关联代码：`models/domain.py::Order`（`exact_address`、`parent_phone`）、
  `routers/v1/orders.py::address-unlock`、`services/serializers.py`

## 背景

`orders` 表以明文存储家长手机号与真实门牌地址。当前防护全部是**可见性层面**的
（ADR-0002：序列化脱敏 + address-unlock 卡点），数据库文件/备份/拖库场景下 PII 直接裸露。
业务量增长后（尤其对接企业客户或等保/个保法审查），静态加密会从加分项变成硬性要求。

本 ADR 只做决策评审，**不包含实施**。实施属单独排期（涉及存量数据回填迁移，需停机窗口评估）。

## 提议方案

### 算法与形态

1. 对称加密采用 **AES-256-GCM**（认证加密，防篡改）；Python 侧用 `cryptography` 库的
   `AESGCM`（需新增依赖，pin 版本）。
2. 密文列存 base64(nonce(12B) + ciphertext + tag(16B))，nonce 每次加密随机生成、随密文同存。
3. 明文不出现在任何日志、CSV 导出之外的业务输出中；数据库层只见密文。
4. **可检索性**：家长电话需要"按号查单"（客服/对账场景）。对电话额外存
   `phone_search_hash = HMAC-SHA256(pepper, E164号码)`，等值查询走 hash 列，
   不解密全表。地址无等值检索需求，只存密文。

### 密钥管理

1. 主密钥（KEK）不经 .env 明文进 git——通过部署环境变量注入（`PII_ENC_KEY`，base64 32B），
   compose/服务器人工配置。
2. 支持密钥轮换：列内密文带 `key_version` 前缀（如 `v1:...`）；新写用最新版本，
   读取按版本选密钥；轮换 = 新增版本 + 后台批量重加密，不要求一次停机完成。
3. **hash pepper 与加密密钥分离**（`PII_HASH_PEPPER`），轮换策略独立。

### 读写路径变化

- 写：`batch-import` / 订单编辑（`PATCH /orders/{id}`）在入库前加密两字段；
- 读（B 端明文）：`order_fields(sensitive=True)` 处解密；
- 读（脱敏/缓存）：不需要解密——GEO/橱窗缓存只依赖坐标与模糊地址，维持现状；
- `address-unlock`：解锁时解密返回，行为不变；
- CSV 导出：B 端导出仍输出明文（租户隔离保护），在导出路径解密。

## 影响面与风险

1. **存量回填**：需要一次性迁移（读明文→写密文→置空原列或保留双列过渡），
   回填期间新旧格式共存，读取端必须兼容"明文遗留行"。
2. `_ensure_*` 双轨现状（P2-1）会放大迁移复杂度——**建议先完成 P2-1（database.py 收敛）再实施本 ADR**。
3. LIKE 模糊查询家长电话将不可用（只有 hash 等值查询）；现有代码无此查询，无回归。
4. 备份/从库/开发库（DEV_MODE 种子数据）同样进密文域；本地开发需配 `PII_ENC_KEY`
   或明确降级为"DEV_MODE 下不加密"（推荐后者，保持开发零感知）。

## 备选与否决

- **应用层 FPE（格式保留加密）**：保格式但实现复杂、安全强度弱于 GCM，否决；
- **数据库层 TDE/磁盘加密**：只防介质丢失，不防 SQL 注入/拖库凭证，作为补充不作为方案；
- **不加密，仅收紧访问**：个保法合规审查下不达标，否决。

## 实施前置条件

1. P2-1 完成（`_ensure_*` 退役，迁移链唯一事实源）；
2. 评审通过本 ADR 的密钥管理与检索方案；
3. 有备份回滚演练窗口。

满足前，维持现状：ADR-0002 的可见性防护 + 数据库访问控制。
