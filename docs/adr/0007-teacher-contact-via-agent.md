# ADR-0007: 教员对接流程对齐真实业务（中介套中介），家长联系方式不进入教员链路

- 状态：**已接受（Accepted）**——已实施（提交 d226652）
- 日期：2026-09-25
- 关联代码：`routers/v1/orders.py::get_order_detail`、`services/serializers.py::order_detail_payload`、
  `frontend/src/views/teacher/OrderDetail.vue`、`routers/v1/orders.py::address_unlock`
- 关联决策：ADR-0002（PII 脱敏）、ADR-0005（PII 静态加密，草案）

## 背景

产品最初按"教员试课后解锁家长真实电话与门牌号"设计（`/address-unlock` 卡点）。
用户（运营方）指出真实业务形态是**中介套中介**：平台上的"中介"是渠道方，
教员投递后全程通过微信与对接中介沟通（确认试课、课酬、上门细节），
**教员不需要也拿不到家长的直联方式**。解锁功能是产品想象出来的流程，真实世界不存在。

## 决策

1. **教员端 UI 下线家长联系方式入口**：订单详情的解锁区块替换为
   「我的投递 · 联系对接中介」——展示中介微信（可复制）+ 投递消息预览 +
   一键复制（含订单编号/内容/教员姓名），教员粘进微信完成对接。
2. **接口层维持脱敏红线**：`order_detail_payload(include_sensitive=False)` 继续对
   教员剥离 `exact_address`/`parent_phone` 并掩码 `raw_text`；同时新增
   `contact_wechat` 下发（仅教员视角，B 端拥有该数据无需回传）。
3. **前端客户端删除 `addressUnlock` 方法与 `AddressUnlockResponse` 类型**
   （死代码防误用）；后端 `/address-unlock` 端点**保留**（API 兼容 + 状态门禁不变），
   但补 `record_audit(ACTION_UNLOCK)`——PII 出口只要存在就必须可追溯。
4. **话术校正**：投递成功提示、帮助中心、简历弹层等处的"家长"统一改为
   "对接中介"，与真实业务一致。
5. 「我的投递」卡片整卡可点进详情（此前试课前无任何详情入口，属缺口）。

## 后果

- 教员链路的 PII 暴露面从"可解锁"降为"结构性不可达"——家长联系方式成为
  B 端专属数据，ADR-0002 的脱敏防线从"前置卡点"变成"双保险"。
- ADR-0005（静态加密）的实施紧迫度下降：数据不再流向教员端，暴露面只剩
  中介后台与数据库层。是否仍实施该 ADR 待业务规模增长后再评估。
- 隐私政策（/privacy）的表述与实际防护一致，不再承诺未实施的加密能力。

## 备选与否决

- **保留解锁功能并加频控/水印**：与真实业务流程不符，教员拿到家长电话反而
  绕过中介产生纠纷与飞单风险，否决；
- **直接删除后端 unlock 端点**：破坏 API 兼容且牵动状态机测试（unlock_requires_trial
  资金守卫依赖其门禁语义），保留 + 审计是风险最低的收缩方式。
